A vesting vault, three Major findings, then a pass.

This is a reference build: a revocable ERC-20 token-vesting vault we designed and delivered to ourselves. There was no client, and nothing was deployed.

First review: REVISE

The independent adversarial reviewer returned REVISE with three Major findings.

Finding 1: a subtraction that runs too early

The release formula was correct, and so was the branch order in the spec's pseudocode. What the spec never said was that t - start may only be evaluated after the branch guard holds. Solidity 0.8 arithmetic is checked, so an implementation that computes it first reverts whenever the current time is before the start date.

The result: every view and every revoke touching a schedule would revert until that schedule's start date. Scheduling vesting ahead of time is the normal case.

The fix was to write the rule into the spec and add boundary acceptance tests that fail if the order is ever swapped. In the corrected form, the subtraction lives only inside the branch where it is valid.

Finding 2: no pre-mainnet safety requirement

The design did not require a third-party audit and a testnet rehearsal before mainnet. That requirement is now in it.

Finding 3: no defined return before start

The design did not define what to return for a timestamp before the start date. That return is now defined.

Second review: PASS

All three findings were fixed, and the second review passed.

Our own gate failed open, too.

One of our gates passed 44 green tests. An independent review then found it silently skipping functions whose security intent was missing or misspelled.

We changed it to block anything it cannot classify. The test count went from 44 to 51.

What this case study is not

It is not client work, and nothing here was deployed. It shows how our review loop behaves on a real design, including when the problem is in our own tooling.
